Read queries run directly against the current graph, with no change to open first.

The examples on this page use a small graph of people, companies and interests. Create it once in a change (see [Writing data](/query/writing)) if you want to follow along:

```cypher
CREATE
  (alice:Person {name: 'Alice', age: 30, city: 'London', active: true, tags: ['admin', 'vip']}),
  (bob:Person {name: 'Bob', age: 35, city: 'London', active: true, tags: ['dev']}),
  (carol:Person {name: 'Carol', age: 28, city: 'Paris', active: false, tags: ['dev', 'vip']}),
  (dave:Person {name: 'Dave', age: 41, city: 'Paris', active: true}),
  (acme:Company {name: 'Acme', founded: 1999}),
  (globex:Company {name: 'Globex', founded: 2010}),
  (music:Interest {name: 'Music'}),
  (alice)-[:KNOWS {since: 2010}]->(bob),
  (bob)-[:KNOWS {since: 2015}]->(carol),
  (carol)-[:KNOWS {since: 2018}]->(dave),
  (alice)-[:WORKS_AT {role: 'CTO'}]->(acme),
  (bob)-[:WORKS_AT {role: 'Engineer'}]->(acme),
  (carol)-[:WORKS_AT {role: 'Engineer'}]->(globex),
  (alice)-[:LIKES]->(music),
  (carol)-[:LIKES]->(music)
```

## MATCH

```cypher
MATCH (n)
RETURN count(n)

MATCH (n:Person)
RETURN n.name, n.age

MATCH (n:Person {name: 'Alice', age: 30})
RETURN n.name

MATCH (n:Person:Employee)
RETURN n.name

MATCH (a:Person)-[:KNOWS]->(b:Person)
RETURN a.name, b.name

MATCH (a)-[e:KNOWS {since: 2010}]->(b)
RETURN a.name, e.since, b.name

MATCH (a)<-[e]-(b)
RETURN a.name, b.name

MATCH (a)-[e]-(b)
RETURN a.name, b.name

MATCH (a)-[r:KNOWS|WORKS_AT]->(b)
RETURN a.name, type(r), b.name

MATCH (a {name: 'Alice'})
MATCH (a)-[:KNOWS]->(b)
RETURN b.name
```

- `(n:Person:Employee)` matches nodes that have **both** labels.
- `(a)-[e]-(b)` (or `(a)--(b)`, `(a)<-[e]->(b)`, `(a)<-->(b)`) ignores direction.
- `[:KNOWS|WORKS_AT]` matches either edge type. An edge has exactly one type, so each edge pattern takes a single type or a list of alternatives.
- `type(r)` returns the edge type as a string.
- Several `MATCH` clauses in a row are allowed, and a later one can reuse variables from an earlier one.
- Variables are only needed for entities you want to return or reuse. `MATCH (:Person)-[:KNOWS]->(m) RETURN m.name` is valid, and a node or edge may omit its variable when it has a label or type.

<Tip>
  `RETURN n` returns the node's internal ID, not its properties. Return the properties you need (`RETURN n.name, n.age`). This is different from Neo4j, where `RETURN n` returns the whole node.
</Tip>

### Label expressions

Label expressions combine labels with `|` (or), `&` (and) and `!` (not), on nodes and on edge types:

```cypher
MATCH (n:Person|Company)
RETURN n.name

MATCH (n:!Person)
RETURN n.name

MATCH (n:Person&Employee)
RETURN n.name

MATCH (n:(Person&!Employee)|Company)
RETURN n.name

MATCH (a)-[r:!KNOWS]->(b)
RETURN type(r), count(*)
```

The same expressions work as tests in `WHERE`: `WHERE n:Person|Company`. A label or an edge type can also come from a [query parameter](/query/cypher_subset#query-parameters): `MATCH (n:$label)`.

### Filtering inside the pattern

A `WHERE` can sit inside a node or edge pattern. The variable must be named:

```cypher
MATCH (a:Person WHERE a.age > 30)-[r:KNOWS WHERE r.since > 2012]->(b)
RETURN b.name
```

### Ordering and limiting in `MATCH`

As a TuringDB extension, `ORDER BY`, `SKIP` and `LIMIT` can also appear right after the pattern, before `RETURN`:

```cypher
MATCH (n:Person)
ORDER BY n.age LIMIT 2
RETURN n.name
```

<Note>
  Unknown labels and property names are forgiving: `MATCH (n:Nope) RETURN n` returns no rows and `RETURN n.misspelled` returns `null`. Use [`CALL db.labels()`, `CALL db.edgeTypes()` and `CALL db.propertyTypes()`](/query/procedures) to check what exists in a graph.
</Note>

## OPTIONAL MATCH

`OPTIONAL MATCH` keeps the row when the pattern has no match and returns `null` for its variables:

```cypher
MATCH (a:Person)
OPTIONAL MATCH (a)-[:WORKS_AT]->(c:Company)
RETURN a.name, c.name

MATCH (a:Person)
OPTIONAL MATCH (a)-[:KNOWS]->(b)
RETURN a.name, count(b)
```

The second query returns `0` for people who know nobody. A `WHERE` attached to an `OPTIONAL MATCH` belongs to the optional part, so rows are kept, as in Neo4j.

An unmatched node or edge returned on its own (`RETURN c`) is `null`, like its properties.


## WHERE and operators

```cypher
MATCH (n)
WHERE n:Person
RETURN n.name

MATCH (n:Person)
WHERE n.age >= 18 AND n.city = 'London'
RETURN n.name

MATCH (n:Person)
WHERE n.name STARTS
WITH 'A' OR n.name ENDS
WITH 'e' OR n.name CONTAINS 'ro'
RETURN n.name

MATCH (n:Person)
WHERE n.name IN ['Alice', 'Bob']
RETURN n.name

MATCH (n:Person)
WHERE 'admin' IN n.tags
RETURN n.name

MATCH (n:Person)
WHERE n.tags IS NOT NULL
RETURN n.name

MATCH (n:Person)
WHERE n.active
RETURN n.name

MATCH (n)-[e]->(m)
WHERE e:KNOWS AND e.since > 2012
RETURN n.name, m.name

MATCH (p:Person)
WHERE (p)-[:LIKES]->()
RETURN p.name

MATCH (p:Person)
WHERE NOT (p)-[:KNOWS]->()
RETURN p.name
```

- **Label and type tests:** `n:Person` tests a node label, `e:KNOWS` tests an edge type. Combine them with `AND`, `OR` and `NOT`, or write a [label expression](#label-expressions) such as `n:Person|Company`.
- **Pattern predicates:** `WHERE (p)-[:LIKES]->()` keeps the nodes for which the pattern exists. For richer conditions see [`EXISTS` subqueries](/query/subqueries).

| Operators | |
| --------- | - |
| Comparison | `=`, `<>`, `!=`, `<`, `<=`, `>`, `>=`, and chained comparisons such as `1 < x < 3` |
| Null tests | `IS NULL`, `IS NOT NULL` |
| Boolean | `AND`, `OR`, `XOR`, `NOT`, with three-valued logic for `null` as in Neo4j |
| Membership and strings | `IN`, `STARTS WITH`, `ENDS WITH`, `CONTAINS`, `IS [NFC\|NFD\|NFKC\|NFKD] NORMALIZED` |
| Arithmetic | `+`, `-`, `*`, `/`, `%`, `^`. Integer `/` truncates and `^` returns a Double |
| Concatenation | `+` and `\|\|` join strings and lists, and `list + x` appends an element |

Property constraints in a pattern, `MATCH (n {name: 'Matt', age: 20})`, are exactly equivalent to the same equality tests in `WHERE`.

<Note>
  Use `n.prop IS NOT NULL` to test for a property, and `STARTS WITH`, `ENDS WITH` and `CONTAINS` to match strings. Regular expressions (`=~`) and `exists(n.prop)` are not yet supported.
</Note>

### Comparing numbers

Integers and Doubles compare by value, so an Integer `30` equals the Double `30.0`:

```cypher
MATCH (n:Person)
WHERE n.age = 30.0
RETURN n.name

MATCH (n:Person)
WHERE n.age IN [30.0, 35]
RETURN n.name
```

To match one Double against another, use a range. `=` between two Doubles is reported when the query is analysed, because of rounding:

```cypher
MATCH (n:Person)
WHERE n.age * 1.1 > 32.9 AND n.age * 1.1 < 33.1
RETURN n.name
```

Mixed-type `<`, `>` and arithmetic work as expected, and an ordering between values with no common order, such as `1 < 'a'`, is `null`. Division by zero returns an execution error, for Doubles too, and Int64 arithmetic wraps around on overflow.

## Joins and Cartesian products

Comma-separated patterns in a `MATCH` produce either a **join** or a **Cartesian product**, depending on whether they share a variable.

```cypher
// Cartesian product: every Person with every Company (N x M rows)
MATCH (p:Person), (c:Company)
RETURN p.name, c.name

// Join: a shared variable links the patterns
MATCH (a:Person)-[:KNOWS]->(b), (b)-[:WORKS_AT]->(c)
RETURN a.name, b.name, c.name

// Join on a shared node: people who like the same thing
MATCH (a:Person)-->(i:Interest)<--(b:Person)
WHERE a <> b
RETURN a.name, b.name, i.name

// Join on a value through WHERE (hash join)
MATCH (a:Person), (b:Person)
WHERE a.city = b.city AND a <> b
RETURN a.name, b.name
```

<Warning>
  A Cartesian product of N nodes by M nodes produces N × M rows. Always constrain it with `WHERE` or `LIMIT` before running it on a large graph.
</Warning>

Connected paths and independent patterns can be mixed in one query. Shared variables create joins and unrelated patterns create Cartesian products:

```cypher
MATCH (a:Person)-->(i:Interest), (c:Company)
WHERE c.name = 'Acme'
RETURN a.name, i.name, c.name
```

## Look up nodes by native node ID

Every node has a **native node ID**, the integer you get from `RETURN n` or `id(n)`. When you already know which nodes you want, compare the node with its ID, `WHERE n = 123` or `WHERE id(n) = 123`. TuringDB then looks those nodes up directly instead of scanning the graph:

```cypher
MATCH (n)
WHERE n = 0
RETURN n.name

MATCH (n)-[:KNOWS]->(m)
WHERE id(n) = 0
RETURN m.name

UNWIND [0, 1, 2] AS x
MATCH (n)
WHERE n = x
RETURN x, n.name

UNWIND [[0, 1], [2, 3]] AS p
MATCH (a)
WHERE a = p[0]
MATCH (b)
WHERE b = p[1]
RETURN a.name, b.name
```

`EXPLAIN` shows the lookup: the plan contains `const_scan_nodes` for IDs written in the query, or `fetch_nodes` for IDs read from a row, rather than `scan_nodes`:

```cypher
EXPLAIN MATCH (n)
WHERE n = 0
RETURN n.name
```

- **Batches.** `UNWIND` a list of IDs and compare each one: `UNWIND <ids> AS x MATCH (n) WHERE n = x`. The list can be written in the query (`f"UNWIND {ids} AS x ..."` in Python), held in a variable, or built with `collect()` or `range()`, and each ID costs a few microseconds. Use this form rather than `WHERE n IN [...]`, which checks every node.
- **Several IDs per row.** Two IDs from the same row work too, which is the fast way to [create many edges between existing nodes](/query/writing#edges-between-existing-nodes).
- **Fetch IDs once and reuse them.** Look nodes up with whatever filter you need (`MATCH (n:Person {name: 'Alice'}) RETURN id(n)`), keep the IDs in your application, and address the nodes by ID from then on. Looking each row's node up through a key property such as `n.uuid` reads every node with that label instead, and is about 100 times slower on a large graph.
- **Vector search results are already nodes.** `VECTOR SEARCH ... YIELD ids` binds `ids` as nodes, so use `ids.title` or `MATCH (ids)-[...]->(...)` directly. See [Vector search](/vector-search).

**Stability.** The native IDs of existing nodes are stable across queries, change submits and server restarts, so it is safe to cache them. Two exceptions:

- Nodes created in an open change get their final IDs at `COMMIT` or `CHANGE SUBMIT`. Read them after that.
- [`MERGE_DATAPARTS`](/concepts/dataparts) renumbers all nodes. Re-fetch any cached IDs afterwards.

Keep a business key as a property as well, for durable identity outside TuringDB. Use `id(n)` for node IDs. For edges, `MATCH ()-[r]->() WHERE id(r) = 0 RETURN startNode(r), endNode(r)` works.
